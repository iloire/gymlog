# Two languages: English and Spanish

Written 2026-09-21. The app is English only, and every word of it is a literal in a component.
This is the plan for making it read in Spanish too, without touching the two non-negotiables:
every screen still renders off Dexie with no signal, and the language is an account fact like the
unit, never something the request payload gets to say.

**Sizes** as in `docs/roadmap.md` — **S** under a day · **M** one to three days · **L** more.
Every phase ships behind a passing `npm test` and one commit per screen or step, so several agents
can work it in parallel without meeting in the same file.

---

## 1. Decisions

### 1.1 No locale in the URL

Next's own guide reaches for `/es/session`. Not here. The service worker precaches a fixed list
of paths and falls back to `/` for any navigation with no signal; `ignoreSearch` on `/session`
relies on one document per route; deep links, the open-workout bar, `redirects` in
`next.config.ts` and every `href` in the app assume one path per screen. A path prefix would
double all of that for no gain: nobody shares a gymlog URL for its language. The locale is a
property of the person, so it travels the way the unit does.

### 1.2 The language is an account setting, mirrored to a cookie on each device

Same shape as `users.unit`, for the same reason: you think in one language wherever you are, so
the choice goes up with the next sync and the other phone follows. Concretely:

- `users.locale TEXT NOT NULL DEFAULT 'en'`, enum `['en', 'es']`, new migration. **Prod
  migrations are manual** (`npm run db:migrate:prod`); sync 500s until it has run.
- `/api/sync` accepts `locale` in a push and returns it in every response, exactly like `unit`
  (`app/api/sync/route.ts:42-69`). The client keeps `meta.locale` and `meta.localePending` the way
  it keeps the unit (`lib/sync/client.ts:25-27, 210-216, 251-266`). Do not copy the unit code a
  second time: fold both into one `syncedPreference('unit' | 'locale')` helper so a third
  preference is a one-liner.
- A cookie `gymlog:locale` on the device carries the same value, so the **server** knows it before
  Dexie is open. The server needs it for `<html lang>`, for the pre-login screens, for the two
  server-rendered desk pages, and so the shell it renders is already in the right language and
  nothing flashes English on the way in. Whoever writes `meta.locale` (the Language page, or a
  sync that brings the other phone's choice) writes the cookie too.
- A visitor with no cookie gets one from `Accept-Language`, negotiated in `proxy.ts`, which
  already runs on every navigation. `negotiateLocale(header)` is pure and tested: `es-MX,es;q=0.9`
  → `es`, anything else → `en`. Signup seeds `users.locale` from that cookie, so an account
  created from a Spanish phone starts in Spanish and its first sync does not flip it back.
- `/api/v1/profile` reports `locale` beside `preferredUnit`; the backup file carries it beside
  `unit` if it carries `unit` at all (check `lib/backup.ts` when you get there).

Theme stays per device and equipment stays per device. Language is not like them: a shared phone
is handled by logout wiping the database, and the next login's first sync rewrites the cookie.

### 1.3 `next-intl`, without its routing

`next-intl` 4.14 (peer `next ^16`) in its "without i18n routing" mode: locale from the cookie,
ICU messages with plurals and placeholders, typed message keys, `useTranslations()` in client
components and `getTranslations()` in the two server pages. What it buys over a hand-rolled `t()`
is exactly the parts that go wrong by hand: plural rules, placeholder checking, and formatted
dates and numbers per locale. Two things it must **not** do here:

- **No server round trip to switch language.** Its normal setup loads one language's messages per
  request; switching means `router.refresh()`, which fetches an RSC payload and fails offline.
  Instead a client `LocaleProvider` (in `components/`, wrapping `NextIntlClientProvider`) imports
  **both** bundles, holds `locale` in state initialised from the cookie the layout read, and
  swaps `messages` locally when the Language page or a sync changes it. Two bundles is roughly
  twice 40 kB of JSON in the client chunk, cached by the service worker like any other asset.
- **Fall back to English, never throw.** Messages are `deepMerge(en, es)` at import, so a screen
  translated after another agent added a string still renders, in English, instead of erroring.
  The test in §5 is what keeps the gap from lasting.

### 1.4 One messages file per screen, so agents do not collide

Several agents work this checkout at once. A single `es.json` would be the one file every task
touches. So: `messages/<locale>/<screen>.json` — `session.json`, `today.json`, `plan.json`,
`exercises.json`, `history.json`, `weight.json`, `profile.json`, `auth.json`, `common.json` (nav,
buttons, sync badge, undo toast, the rest timer), `data.json` (body parts, muscles, equipment,
levels, programmes). `messages/index.ts` assembles them into one namespaced object per locale.
A screen's commit touches its own two JSON files and its own components, nothing else.

English is the source of truth and lives in the JSON too, not in the components: a component says
`t('startWorkout')` and nothing else. Keys are short camelCase names of what the string is *for*
(`emptyWeek`, `setsDone`), never the English text.

### 1.5 The exercise library is translated as an overlay, not a column

873 library exercises with English names and instructions sit in the synced `exercises` table
with `userId IS NULL`. Adding `name_es` columns means a migration, a sync change and a reseed for
every language ever added. Instead ship `data/exercises.es.json`: `{ "<exercise id>": { "name":
"Sentadilla con barra", "instructions": [...] } }`, applied at display time by
`exerciseName(exercise, locale)` and `exerciseInstructions(exercise, locale)` in a new
`lib/exercise-i18n.ts`. A user's own exercises have no entry and show as typed. The overlay is
bundled, so it works with no signal; names are ~30 kB and go in the main chunk, instructions are
~500 kB and are a dynamic `import()` from the exercise dialog and page only, which the service
worker caches first like any hashed asset.

Search (`filterExercises`) must match the Spanish name **and** the English one: "press de banca"
and "bench press" both find the row. Sort by the displayed name.

Producing the file: a one-off script machine-translates name and instructions, then it is read
through by hand before it is committed. The reviewer keeps the anglicisms a Spanish gym actually
uses (*press de banca*, *curl*, *peso muerto*) rather than the literal rendering. The script is
throwaway; the JSON is what ships. Names first (one commit), instructions second (one commit).

### 1.6 What stays English

- `/api/v1`, its OpenAPI document and every API error string: it is for an LLM, and the tokens
  page says so.
- Server-to-client codes: sync rejection `reason`s, signup `error` values. Codes cross the wire;
  words are chosen on the device from the code.
- Exercise ids and slugs, equipment ids, body part and muscle ids, programme ids, workout keys.
  Ids are the English strings today (`'Legs'`, `'barbell'`); they keep their value and get a
  display name from `data.json`. Do not rename an id to translate it.
- Log lines, comments, commit messages, the docs.

## 3. Phase 2 — every string, one screen per commit (L, mechanical)

In gym order, so the screens that get used with chalk on your hands go first. Each is one
commit: move the screen's literals into its two JSON files, replace with `t()`, translate. The
rough literal counts are from a grep of JSX text and `aria-label` / `placeholder` / `title`
attributes and overstate a little, but they size the work:

| Commit | Files | Literals |
|---|---|---|
| session | `app/session/page.tsx`, `session-sets`, `set-squares`, `stepper`, `plate-rail`, `effort-chips`, `rest-timer`, `finish-session`, `workout-summary`, `exercise-note` | ~430 |
| today | `app/page.tsx`, `week-strip`, `open-workout-bar`, `plan-list`, `exercise-dialog`, `exercise-detail` | ~190 |
| plan | `app/workouts/**`, `workout-sheet`, `item-sheet`, `day-picker`, `exercise-picker`, `remove-exercise`, `app/programmes/page.tsx` | ~330 |
| exercises | `app/exercises/**`, `exercise-filters`, `favorite-button`, `body-part-badges`, `equipment-picker` | ~170 |
| history + weight | `app/history/page.tsx`, `training-calendar`, `strength-chart`, `app/weight/page.tsx`, `weigh-in`, `weight-chart`, `delete-session` | ~180 |
| common | `nav`, `sync-badge`, `undo-toast`, `loading`, `overflow-menu`, `session-boot`, `sign-out-button`, `ui/button` | ~130 |
| profile | `app/profile/{page,appearance,equipment,units,data}`, `theme-picker` | ~150 |
| auth | `app/(auth)/**`, `auth-shell`, `auth-hero` | ~80 |
| api tokens + admin | `app/profile/api/**`, `api-access/*`, `app/admin/**` — server pages use `getTranslations()` | ~110 |

Also the handful of user-facing strings in `lib/`: the streak sentences in `lib/calendar.ts`, the
backup errors in `lib/backup.ts`, `'No exercises yet'` in `lib/plan.ts`, `'My programme'` in
`lib/program.ts`, `UNIT_NAMES` in `lib/units.ts`. Pure functions keep returning **keys** (or
codes) and the component renders them, so the tests stay free of React.

Plurals: the 28 `=== 1 ? 'set' : 'sets'` sites become one ICU message each,
`{count, plural, one {# set} other {# sets}}`, which Spanish shares (one / other).

Translation voice: **tú**, short, the imperative where the English is (*Empieza*, *Guardar*,
*Deshacer*). Gym words as a Spanish gym says them: *serie* for set, *repeticiones* / *reps*,
*descanso*, *calentamiento*, *peso corporal*, *entrenamiento* for workout, *programa* for
programme. Keep numbers and the `×` in `80×5`.

## 5. Tests, so the gap never lasts

`tests/i18n.test.ts`:

- Every key in `en` exists in `es` and the other way round, per screen file, so the failure names
  the file. This is the test that turns "I forgot the Spanish" into a red CI, not a silent English
  word on a Spanish screen.
- Every message compiles as ICU, and the placeholders in `es` are exactly those in `en`.
- No message is empty, none still equals its key.
- `negotiateLocale` cases; `parseLocale` rejects `'fr'`.
- Formatting in `es`: `77,5 kg`, `15 sept 2026`, `hace 3 días`, `hoy`, `ayer`, `1 h 5 min`,
  weekday initials.
- Proxy sets the cookie once and never overwrites one that is there.

Break each once and watch it go red before trusting it.

## 6. Verification before calling it done

- Production build, phone width, Spanish: open every tab with the network off. Nothing English on
  a gym screen, nothing overflowing (Spanish runs ~20% longer; the set squares, the nav labels and
  the stepper are the tight spots).
- Switch language on the laptop, sync, watch the phone follow without a reload.
- Sign out, sign in as another account: the phone reads in that account's language.
- Fresh private window with `Accept-Language: es`: the login page is Spanish before any account.

## 7. Out of scope, on purpose

- A third language. The shape allows it (a locale, a folder of JSON, an overlay file), nothing
  else is pre-built for it.
- Translating other people's exercise names or notes. Anything a user typed shows as typed.
- Regional variants (`es-MX`). One Spanish; the formatting locale is `es-ES`.
- Translating the API, the OpenAPI document or the admin panel's data labels beyond the chrome.
